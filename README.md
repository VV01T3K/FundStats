# FundStats

Ranked tables of returns for mBank investment funds and the top cryptocurrencies (CoinGecko, CoinPaprika,
CoinMarketCap).

A background collector calls the providers' APIs on a schedule and stores the results in Postgres. Every page and
API response is served from that database, so visitors never trigger upstream calls.

## Stack

- **Web**: TanStack Start (React 19, Vite 8), TanStack Router (typed, validated search params), TanStack Query
  (SSR-prefetched), TanStack Table v9, shadcn/ui on Tailwind 4.
- **Backend**: Effect 4 in the same process: the collector, an `HttpApi` served under `/api`, config, and the
  database service.
- **Database**: Postgres 18 with Drizzle ORM. SQL migrations are generated by drizzle-kit into `drizzle/`.
- **Tooling**: bun, TypeScript 7, Biome, Vitest with `@effect/vitest`, testcontainers.

## Layout

```
src/
  shared/          code used by both browser and server
    api.ts           HttpApi contract (endpoints and schemas)
    sources.ts       source catalog (name, kind, currency, icon)
    metrics.ts       metric names and the momentum formula
  server/          Effect backend; never imported by browser code
    config.ts        environment, read and checked at boot
    db/              Drizzle schema, Database service (pool + migrations), Store (all queries)
    sources/         one file per upstream: fetch + decode + normalize
    collector/       runs sources once, or on a schedule as background fibers
    api/             HttpApi handlers
    runtime.ts       composition root: one ManagedRuntime + the /api web handler
    cli/             `bun run collect`, `bun run db:migrate`
  web/             React side: typed API client, table configs, components
  routes/          TanStack Router file routes; routes/api/$.ts mounts the Effect API
  server.ts        server entry: boots the runtime before serving requests
drizzle/           generated SQL migrations
test/              tests and saved upstream fixtures
```

## Run locally

Requires bun 1.4+ and Docker.

```sh
bun install
cp .env.example .env                         # DATABASE_URL points to the dev database below
docker compose -f compose.dev.yaml up -d     # Postgres on 127.0.0.1:55432 (FUNDSTATS_DB_PORT changes the port)
bun run collect all                          # fetch every source once (also applies migrations)
bun run dev                                  # http://localhost:3000 (PORT changes the port)
```

When the app starts it applies pending migrations and starts the collector. The collector decides when each source
is due from its last run in the database, so a restart does not call the upstreams again early. To work without
calling the upstreams at all, set `COLLECTOR_ENABLED=false`.

The server runtime is a process-wide singleton, so an HMR reload never starts a second collector or connection pool.
In return, edits under `src/server/` only reach the running collector and API after you restart `bun run dev`.

### Scripts

| Command                   | What it does                                                          |
| ------------------------- | --------------------------------------------------------------------- |
| `bun run dev`             | Dev server with HMR                                                   |
| `bun run build`           | Production build to `.output/`                                        |
| `bun run start`           | Run the production build (`node .output/server/index.mjs`)            |
| `bun run collect <id>`    | Run one source once: `mbank`, `coingecko`, `coinpaprika`, `coinmarketcap`, or `all` |
| `bun run db:migrate`      | Apply migrations without starting the app                             |
| `bun run db:generate`     | Generate a migration after changing `src/server/db/schema.ts`         |
| `bun run typecheck`       | TypeScript                                                            |
| `bun run lint`            | Biome lint + format check (`bun run format` fixes)                    |
| `bun run test`            | Vitest; starts a throwaway Postgres container                         |

The tests never call a live upstream. They read saved samples from `test/fixtures/`. To use an existing empty
database instead of a container, set `TEST_DATABASE_URL` (the tests truncate its tables).

## Deploy (Docker Compose)

`compose.yaml` runs the app and Postgres. The database sits in a named volume and has a healthcheck, and the app
waits until the database is healthy.

```sh
cp .env.example .env     # set POSTGRES_PASSWORD; optionally FUNDSTATS_PORT, API keys, intervals
docker compose up -d --build
docker compose logs -f app
```

The app applies migrations when it starts. To update, pull and run `docker compose up -d --build` again. Postgres
is not published on the host. To back it up, run
`docker compose exec db pg_dump -U fundstats fundstats > backup.sql`.

Put a reverse proxy (Caddy, nginx, Traefik) in front of it for TLS.

### Configuration

All settings are environment variables, read through Effect `Config`. An invalid value stops the app at boot. See
`.env.example`.

| Variable                         | Default        | Notes                                                    |
| -------------------------------- | -------------- | -------------------------------------------------------- |
| `DATABASE_URL`                   | required       | compose.yaml builds it from `POSTGRES_PASSWORD`          |
| `COLLECTOR_ENABLED`              | `true`         | `false` = never call upstreams                           |
| `COLLECTOR_INTERVAL_<SOURCE>`    | see below      | e.g. `COLLECTOR_INTERVAL_MBANK=6 hours`                  |
| `RAW_PAYLOAD_RETENTION_DAYS`     | `30`           | stored upstream responses older than this are deleted daily |
| `COINGECKO_API_KEY`              | unset          | CoinGecko demo key; raises the rate limit                |
| `CMC_API_KEY`                    | unset          | official CoinMarketCap API; without it the unofficial web endpoint is used |
| `DB_POOL_MAX`                    | `10`           |                                                          |
| `RUN_MIGRATIONS`                 | `true`         | apply migrations on start                                |
| `PORT` / `HOST`                  | `3000`/all     |                                                          |

Default intervals: mBank every 6 hours (its feed changes once per business day), crypto sources every 30 minutes.
After a failed run, the next attempt comes within 10 minutes.

## Data model

- `instruments`: one row per fund or coin per source, unique on `(source, external_id)`. `last_seen_run_id` marks
  the instruments in the source's latest successful run, and the "latest" views list only those.
- `snapshots`: values at a point in time. `value` holds the unit value or price. `metrics` is jsonb with named
  numbers (`change_1m`, `change_7d`, `rank`, …; see `src/shared/metrics.ts`).
  - **Dedupe rule:** mBank values come with a valuation date (`as_of`). Each instrument has at most one row per
    date, and re-collecting the same date rewrites that row only if a value changed.
  - Crypto quotes have no `as_of` and get one row per collection.
- `collection_runs`: every run with its trigger, status, counts and error.
- `raw_payloads`: the upstream response of each run (CoinPaprika trimmed to the top 100), so the data can be
  re-normalized after a bug fix.

Derived values are computed when the data is read, not stored. Weighted momentum,
`(4·1m + 3·3m + 2·6m + 1·1y) / 10`, is defined only in `src/shared/metrics.ts`.

## API

Data endpoints are under `/api/v1`. OpenAPI document: `/api/openapi.json`. Interactive docs: `/api/docs`.

| Endpoint                                                   | Returns                                         |
| ---------------------------------------------------------- | ----------------------------------------------- |
| `GET /api/health`                                          | app and database status                         |
| `GET /api/v1/sources`                                      | each source with its last run, last success and a stale flag |
| `GET /api/v1/sources/:source/latest`                       | source status and the latest row per instrument |
| `GET /api/v1/sources/:source/instruments/:externalId/history?limit=` | snapshots of one instrument, newest first |

The browser uses a client generated from the same definition (`src/web/api.ts`). During SSR that client is answered
in-process, without an HTTP round trip.

## Add a source

1. Add its display metadata to `SOURCES` in `src/shared/sources.ts`.
2. Create `src/server/sources/<id>.ts` with `defineSource({ info, defaultInterval, fetch, normalize })`:
   - `fetch`: build the request and call `fetchJson(id, request, Schema)`. You get timeouts, retries with backoff
     and typed errors from that helper.
   - `normalize`: a pure function from the decoded payload to `NormalizedRow[]`. Use the metric names in
     `src/shared/metrics.ts`; add a new one there if needed.
3. Register it in `src/server/sources/registry.ts`.
4. Add a column config to `TABLES` in `src/web/tables/index.ts`: columns, default sort, and optional periods,
   thresholds or categories.
5. Save a small real response under `test/fixtures/` and add a normalize test.

TypeScript reports an error until steps 1, 3 and 4 all have the new id. The page is then served at
`/funds/<id>` or `/crypto/<id>`, and the collector picks the source up on its next start.
